# Bridge protocol v1

Connect to `ws://HOST:8789/api/v1/events` with `Authorization: Bearer CONNECTION_KEY`. Browser Origin headers are rejected. No credentials belong in a URL.

Every server frame contains `apiVersion: 1`, `type`, `sessionId`, and integer `revision`, and `serverNow` (bridge Unix milliseconds). A new process has a new session ID. Revisions increase only when normalized race data changes.

- `state.snapshot`: `state` contains `competition`, `competitors` and `results`. `competitors`, `results` and optional `active` and `runResults` are objects keyed by stable IDs (`event-N:competitor-ID`). Includes `health`. While the first read is pending, `state` is null and revision is 0.
- `state.delta`: includes `baseRevision`, `changes` and `health`. `changes.competition`, if present, replaces metadata. `changes.competitors`, `changes.results`, `changes.active` and `changes.runResults`, when present, each contain `upsert` objects and `delete` ID arrays. Apply the entire delta atomically, then validate references. A bib change is not a new competitor.
- `health`: sent at least every two seconds while the event loop is responsive; includes `health.ok`, `message` and `lastReadAt` (Unix milliseconds). Database errors preserve the last good state and revision. Socket liveness is not proof of database freshness.

The client sends `{"type":"state.request"}` to get a fresh snapshot. On connection, always accept a new snapshot as authoritative; do not replay its results as finish events. A delta is usable only when its session matches, `baseRevision` equals the client's revision, and `revision` is exactly one higher. Otherwise stop applying deltas and request a snapshot. There is no durable event replay journal.

Competition metadata includes event number, name, subtitle, source version, selected heats, ranking (`heat` or `total`), warnings, `runningTimersSupported` and optional `timingMode` (`simulation` or experimental `records`). In default results-only mode, `runningTimersSupported` is false.

Competitors contain `id`, `bib`, `name`, `category`, `club`, `yearOfBirth` (string or empty string). Results contain `id`, `competitorId`, `bib`, `status` (`finish`, `dns`, `dnf`, `dsq`) and `timeMs` (positive integer for finishes, null for terminal statuses).

HTTP `GET /api/v1/snapshot` returns the same snapshot envelope. `GET /api/v1/health` returns health, revision and client count. Both require the same Authorization header. There are no remote configuration or database-write routes. Localhost-only `/control/*` routes provide validated settings, folder discovery, explicit key copying, competition selection, diagnostic export and (only in simulation mode) commands to the separate replay writer; they are not part of the remote client contract. Selecting another competition starts a new session and sends a snapshot on existing WebSocket connections.

Active racers are keyed by competitor ID and contain `id`, `competitorId`, `bib`, `runId`, `startedAtMs`, `baseTimeMs`, `heat` and `totalEligible`. `runId` distinguishes repeated starts of the same bib. Active `totalEligible` describes validity of the required prior runs, so it is true for a first-heat start. `baseTimeMs` is the sum of selected earlier heat times when every required earlier result is valid, or zero for a single heat. If any earlier result is missing, terminal, penalized or invalid, `totalEligible` is false and `baseTimeMs` stays numeric zero for compatibility; show the individual run clock and mark the total unavailable. Top-level `timing.lastStartAtMs` is the latest accepted start (null if none); `changes.timing` replaces this metadata. The receiver uses active snapshots for clock recovery and compares result deltas to produce finish holds. Full snapshots seed standings silently. Healthy heartbeat frames can re-anchor previously frozen local clocks without resending the roster.

Automatic standings add `competition.autoStandings: true` and `competition.categoryStandings`, an array of `{ category, heats, ranking }`. Use the entry matching the displayed category for labels and heat numbers; categories can be on different heats. Results already contain that category's selected time basis, so clients must not sum times again. A category switches only after a valid cumulative finish; incomplete totals are removed in the same atomic delta. Terminal statuses remain unranked. Corrections and reconnects reconstruct the selection from current rows. With automatic timing, each active racer's start and base time come from its detected heat, independently of the category's standings selection.

Local settings writes and key-copy requests require a control token and same-origin JSON POST. Network updates restart the HTTP/WebSocket listener; clients reconnect to the new configured address/port. This does not expose administration on the LAN.

`runResults` is an additive map of the latest completed individual run outcome per competitor, independent of eligibility for `results` standings. Each entry contains `id`, `competitorId`, `bib`, `heat`, `runId`, `status`, `timeMs`, `totalEligible` and `totalTimeMs`. `timeMs` is the individual run time, or null for DNS/DNF/DSQ. `totalTimeMs` is the valid cumulative finish time through that heat, otherwise null with `totalEligible: false`. For run outcomes, eligibility describes the completed cumulative finish, so DNS/DNF/DSQ always have `totalEligible: false` even if their earlier runs were valid. `runId` matches the accepted START identity when available, otherwise null. A previous heat outcome can remain while a newer heat is active; match both heat and available run identity before producing a finish hold. Full snapshots seed these outcomes silently. Use `results` for standings and `runResults` for individual finish cards; an individual finish without a valid total must not receive a combined rank. Clients that do not use the additive map may ignore it.

When `timing.startStatuses` is omitted, records mode accepts exactly the supported VOLA 14.1.08 manual-start code `131072`; simulation accepts exactly synthetic code `0`. The known cancellation `131073` and DNS/DNF/DSQ codes `131328`, `131584`, `131840` are excluded by the default records mapping. Explicit nonempty integer arrays remain custom overrides, including existing `[0]` configurations. The local settings form uses automatic mapping unless a custom override is enabled and nonblank; blank means automatic. Other VOLA status variants are not inferred. START table columns and date/offset requirements remain unchanged.
